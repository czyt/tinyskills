# 软件包与仓库架构

## 1. 不重写 pacman，明确各层接口

| 层 | 采用 | 发行版自己实现 |
|---|---|---|
| 依赖与事务 | pacman/libalpm | 策略与可观测性，不另建真相数据库 |
| 构建 | PKGBUILD、makepkg、devtools clean chroot | 配方审查、补丁、CI、来源锁定 |
| 分发 | 包归档、repo-add、pacman 仓库 | 签名、镜像同步、世代保留、通道推广 |
| GUI/安装器 | 受限特权后端或既有包服务 | 用户意图、进度、错误解释，不拼 shell 字符串 |
| 升级编排 | 单一 pacman 事务入口 | 预检、恢复集、迁移、重启/健康确认 |

包管理 GUI 不能各自抢锁；安装器、后台升级、应用商店共享互斥与取消策略。取消下载和取消正在提交的事务不是同一件事。不要在包事务脚本内递归运行 pacman。

## 2. 配方与构建

每个自有包至少审查：来源 URL/commit、校验和、`validpgpkeys`（如适用）、许可证、`arch`、`depends`、`makedepends`、`checkdepends`、`provides/conflicts/replaces`、配置 `backup` 字段及安装路径。

- 非特权账户运行 `makepkg`；隔离 clean chroot 构建，不以“它在我的桌面能装”为依据。
- 一个 release 基础元包组合依赖；不要把所有桌面、驱动、用户配置塞进一个大包。
- `/etc` 可变配置正确声明 `backup`；处理 `.pacnew/.pacsave` 需要比较/合并，不能默认覆盖。
- 包安装脚本不收集密码、不弹 UI、不依赖网络、不启动用户桌面；初始化交给受控阶段。
- AUR 配方视作第三方代码：审查并在隔离环境构建，验证产物后签名进入自有仓库；不将 AUR helper 作为受信任系统升级核心。
- `-git` 包与自有补丁内核必须记录源 commit；“每天最新”不是可追溯版本。

## 3. 三条信任链

1. **构建来源链**：上游源码/配方 → 构建器身份 → 包产物。
2. **包安装链**：可信发行版公钥 → keyring 包 → 包签名/仓库数据库 → pacman 验证。
3. **镜像发布链**：发布公钥 → 签名 manifest/checksums → ISO/rootfs；不能只在同一下载站附未签名 SHA 文件。

签名私钥不进 Git、容器镜像、ISO、rootfs 或 agent 日志。主密钥离线、发布子密钥受限、构建与推广分权是可选工程实现；必须至少有泄露后吊销与重新建立信任的操作流程。

## 4. 仓库签名示例

以下变量是已有 CI 注入的**公开指纹与暂存路径**；只演示签名操作，不生成或展示私钥：

```bash
gpg --batch --local-user "$SIGNING_FINGERPRINT" --detach-sign \
  "$STAGING/mydistro-settings-1.0-1-any.pkg.tar.zst"
repo-add --sign --key "$SIGNING_FINGERPRINT" \
  "$STAGING/mydistro.db.tar.zst" \
  "$STAGING/mydistro-settings-1.0-1-any.pkg.tar.zst"
```

正式流水线处理完整包集合、已存在版本、数据库/签名/链接、repo-files 与镜像保留，不能把该单包示例当完整发布器。

自有仓库使用包和数据库都强制验签的 stanza，例如：

```ini
[mydistro]
SigLevel = PackageRequired DatabaseRequired TrustedOnly
Server = https://packages.example.invalid/generations/2026-10-29/$arch
```

该域名是不可用的说明占位符，换成受控签名源再运行。**不要把这一要求未经检查全局套到 Arch 上游仓库**：上游配置可能允许数据库无签名，但包仍必须验签。检查实际 `pacman.conf` 层级覆盖；`TrustedOnly` 不是忽略信任。

## 5. 仓库世代与通道

一个可部署世代含：架构、上游基线/快照、自有包与数据库摘要、keyring 版本、兼容内核/驱动、迁移版本、镜像来源、验证结果。稳定通道是**推广已验证的同一组字节**，不是在 stable 再构建一次。

上游来源有两条诚实路线：

- **跟随滚动仓库**：持续测试最新版；接受上游滚动时窗，不能宣称整个系统已冻结。
- **控制完整受测组合**：锁定并保留上游与自有仓库的兼容集合，制定安全更新和存储/镜像成本策略。只冻结自有包、任由上游滚动，可能制造部分升级。

发布使用不可变世代路径、先上传包再发布数据库/签名和通道指针；保留旧包以覆盖镜像同步与旧客户端窗口。仓库中的包不能在同名同版本下原地替换。

签名证明来源，不自动防止重放旧的合法数据库。若产品需要防回滚/过期保护，增加受签名的世代元数据、客户端最低允许版本/有效期和离线时钟策略；不要声称 pacman 默认提供完整 TUF 式保护。

## 6. 密钥轮换与故障

先通过旧可信链分发包含新公钥/信任的 keyring 更新 → 验证旧设备接受新签名 → 并行窗口 → 推广新签名 → 发布吊销与救援路径。密钥已泄露时不要只用泄露密钥签一份“相信我”的替代公告，需可信的带外恢复渠道。

| 触发条件 | 一线处理 | 仍失败 |
|---|---|---|
| 验签报错 | 查时间、指纹、keyring、镜像是否处于同步中 | 停止，使用已验证镜像/世代，不设 `TrustAll/Never` |
| 包文件 404 | 查数据库与包上传顺序、镜像保留 | 回退通道，不临时替换同版本文件 |
| pacman 锁存在 | 确认进程、日志、事务是否仍在运行 | 进入恢复流程；不能直接删锁强行并发 |
| ABI/依赖冲突 | 在完整仓库组合复现，整组重建/升级 | 阻止推广；不以全局 `--overwrite '*'` 掩盖冲突 |
